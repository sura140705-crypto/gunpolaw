# 아키텍처 효율성 분석 (실측 기반)

작성 2026-06-26. 질문: "가볍게 가려던 게 분석엔진 2개·DB 2개로 번졌다. 효율적으로 가려면?"

## 0. 한 줄 결론
무거움의 원인은 **데이터량이 아니라 중복**이다. 같은 일을 하는 코드가 2~3벌, DB 2벌, 게다가 **법령 본문을 한 번도 저장 안 해서 매 배치마다 전건 재다운로드**한다. 단일 엔진·단일 DB·"배치 1회 → DB만 서빙"으로 가면 코드는 ~1,900줄 줄고 재배치 API는 대폭 감소한다.

## 1. 실측 현황
### 코드 규모 (총 3,633줄)
| 파일 | 줄 | 역할 | 중복? |
|---|---|---|---|
| `file1.py` | 1,373 | HTTP서버 + 수집 + 추출 + check_freshness | 추출·검증이 gunpolaw와 중복 |
| `phase6.py` | 560 | 라이브 조항검증 + 토큰화 + 본문파싱 | **전부 중복**(checks/clauses/moleg와) |
| `gunpolaw/*` | 1,700 | 신규 단일파이프라인(배치·findings·권고) | 정본 |

### 중복 목록 (같은 기능 N벌)
- **인용 추출**: `file1.py:ref_spans_for_articles/extract_all_refs` ↔ `gunpolaw/extract.py` — 2벌. (맨몸 인용 수정이 한쪽에만 들어가 STEP1/2엔 누락된 바로 그 원인)
- **법령 본문 파싱**: `phase6.parse_law_articles` ↔ `moleg.parse_law_articles` — 2벌
- **조항 토큰화**: `phase6.tokenize_clauses` ↔ `gunpolaw/clauses.py` — 2벌
- **법령ID·본문 조회**: `phase6.resolve_law_id/get_law_body` ↔ `moleg` — 2벌
- **변경 판정**: `phase6.check_clause_freshness`(조문시행일자 기반=옛 부정확 신호) ↔ `checks.diff_clause`(개정태그 기반=정확). **둘이 답이 다름** → STEP3 `<details>` 라이브검증은 메인 권고보다 부정확.

### 데이터베이스 2벌
| DB | 크기 | 내용 | 문제 |
|---|---|---|---|
| `gunpo_ordinances.db` | **9.95MB** | ordinances+body_xml (640) | STEP1/2 전용. 본문 영속 |
| `gunpolaw.db` | 2.44MB | ordinances(본문 없음)+findings(2464)+links | 배치 전용 |
- `gunpolaw.db`의 **`laws`·`law_articles`·`citations` 테이블은 정의돼 있으나 INSERT가 0건 — 죽은 스키마**.
- 조례 본문이 한 DB엔 저장(legacy), 다른 쪽은 매번 재다운로드 → **본문을 두 번 받는다**.

## 2. 진짜 비효율 4가지 (우선순위)
1. **법령 본문 미영속 → 매 배치 전건 재호출.** `pipeline`은 in-memory `law_cache`만 쓰고 끝나면 버린다. `laws`/`law_articles` 테이블(캐시용으로 설계됨)이 비어 있어, 재배치할 때마다 640조례 본문 + 수백 법령 본문 + (deep)버전목록·당시본문을 **전부 다시 받는다**(≈30분 반복). → 가장 큰 낭비.
2. **deep(당시 시행본) 호출이 판정엔 거의 불필요.** 현재 합의 로직은 `diff_clause`가 **현행 본문의 꺽쇠 개정태그**로 판정한다(`basis_dates(cur)`). 당시 본문(old_arts)은 **[당시] diff 표시·번호이동/삭제 추적에만** 쓰인다. 즉 가장 비싼 호출(법령별 `list_versions`+버전본문)이 *판정*엔 안 들어간다 → **표시용으로만 lazy 호출**하면 배치가 크게 가벼워진다.
3. **엔진/DB 중복** → 유지보수 폭증. 버그를 한쪽만 고치게 됨(맨몸 인용 사건이 증거).
4. **UI가 라이브 API에 의존**(phase6 check_clause). 배치본이 있는데도 클릭마다 법제처 호출 → 느리고 부정확·중복.

## 3. 목표 아키텍처 — "배치 1회 → DB만 서빙"
```
[수집·분석 배치 1회]  ── gunpolaw 단일 엔진 ──►  gunpolaw.db (단일)
   조례목록/본문                                   ├ ordinances(+body)
   법령 본문(영속캐시!) ◄── 2회차부터 재사용        ├ laws / law_articles  (캐시 활성화)
   인용추출(span 포함)                              ├ citations (span)  ← STEP1/2 하이라이트도 여기서
   변경판정(개정태그)                               └ findings (권고)
                                                          ▲
[file1.py = 얇은 셸]  HTTP + UI 서빙, /api/* 는 DB만 읽음 (라이브 API 0)
[phase6.py 폐기]      라이브 검증 제거(배치본으로 대체)
```
원칙:
- **엔진 1개**(gunpolaw). file1.py는 추출·검증 로직을 들고 있지 않고 gunpolaw 호출·DB조회만.
- **DB 1개**(gunpolaw.db). gunpo_ordinances.db 폐기(본문은 gunpolaw.db ordinances.body로 흡수).
- **법령 본문 영속 캐시**(`laws`/`law_articles` 채우기). 재배치는 증분(법령ID별 최신 확인 후 변경분만).
- **deep는 표시용 lazy**: 판정은 현행본 개정태그로, [당시] 본문은 권고를 펼칠 때만 조회(또는 배치에서 변경건만).
- **UI = DB 서빙**: STEP1 검색·STEP2 하이라이트·STEP3 권고 모두 DB에서. citations에 span 저장하면 하이라이트도 재호출 없이.

## 4. 기대 효과
- **재배치 API**: 법령 본문 캐시 + deep lazy로 2회차부터 대폭 감소(전건 재다운로드 제거).
- **코드**: phase6(560) 폐기 + file1.py 추출·검증 제거(수백 줄) → 레거시 ~1,900줄 → 얇은 셸 수백 줄.
- **정합성**: 엔진 1개라 "한쪽만 고쳐짐" 버그 소멸(맨몸 인용이 STEP1/2/3 자동 일관).
- **속도**: UI 클릭당 라이브 API 0 → 즉시 응답.
- **DB**: 9.95+2.44MB 2벌 → 1벌(본문 1회 저장).

## 5. 이행 계획 (점진·각 단계 독립검증, 한글 커밋)
1. **법령 본문 영속 캐시 켜기**: `pipeline`이 `laws`/`law_articles`에 저장·우선조회. 재배치 즉시 빨라짐. (위험 낮음, 효과 큼 → **먼저**)
2. **추출 엔진 일원화**: `extract.py`에 span 추가 → `citations` 저장 → file1.py 하이라이트가 DB/gunpolaw 사용. file1.py 중복 추출기 제거. (맨몸 하이라이트 자동 해결)
3. **조례 본문 단일화**: gunpolaw.db `ordinances.body` 채우고 STEP1/2가 그걸 사용 → gunpo_ordinances.db 폐기.
4. **deep lazy화**: 당시 본문 호출을 변경의심건/펼침시로 한정.
5. **phase6 폐기 + STEP2/3 통합**(별도 설계서 `통합뷰_설계.md`).

## 6. 트레이드오프 / 결정 필요
- **gunpo_ordinances.db 폐기**: STEP1 검색의 담당과(dept) 등 legacy 전용 컬럼 이전 필요. (이전 후 폐기)
- **라이브 즉시검증 완전 제거?**: 배치 안 된 신규 조례를 즉석 분석하는 시나리오가 필요하면 phase6 대신 gunpolaw.pipeline을 단건 라이브 호출(`analyze_ordinance`)로 재사용 가능 — phase6는 그래도 폐기.
- **증분 배치 정밀도**: 법령 개정 감지를 어디까지(공포일자/최신 시행일 비교) — 1단계는 단순 캐시, 증분은 후속.
- **호(號) 본문**: moleg.parse_law_articles는 호 미포함, phase6는 포함. 일원화 시 호 포함 버전으로 통일 권장.
